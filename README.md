# APPLICATION-SYSTEM + Application Creation

Integrated from [APPLICATION-SYSTEM](https://github.com/sachindraf1234/APPLICATION-SYSTEM) (base commit `8136777`) and [CV-BUILDER](https://github.com/sachindraf1234/CV-BUILDER) (commit `8b62f00`). The original operational sections, registry and JSON-backed Express server remain in place. Application Creation appears immediately under Master Registry.

## Application Creation workflow

1. Open **Application Creation**. Use **Search candidate by name** to select an existing registry candidate and prefill a new application; selecting a candidate replaces the current editor data, so save the current application first. You may also edit the current form manually.
2. Use **Search application** to reopen a previously saved application by candidate name, passport or application ID. **Save Draft** creates/updates a database-backed application; **Delete saved** deletes the application only, not the candidate. A browser-local draft is also kept as a backup.
3. The **Application created applicants** table shows saved applications, including unlinked ones. The **Application creation pending applicants** table shows registry candidates with no linked saved application. Both tables are searchable and have **Download table PDF**. A candidate leaves Pending only once a linked application is saved.
4. The embedded three-layout editor supports manual data entry, document uploads, signature tools, single/batch processing, and PDF, JPEG ZIP, offline HTML and JSON exports. Downloads go to your device rather than being stored as server documents. Use **Back** to return to the previous main-app section.

## E-Visa Application (from e-v)

The archived source bundles synthetic Embassy Pending fallback fixtures rather than real applicant seed identities; the operator's separate local database is not included in the ZIP. To save applicant work, select an existing candidate before editing; opening a candidate replaces any unsaved blank-workspace entries. It adapts [e-v](https://github.com/sachindraf1234/e-v) (source commit `77549e7`) into the same registry-backed system: search an existing candidate, prefill only actual registry/passport/embassy details, edit visa selection, personal data, family/spouse, passport and occupation, home address, host, company contact, costs, visa request and journey; choose a stage entry and save/reopen/delete a database-backed draft. The original e-v **AI Extractor** is present as its own tab with categorized PDF/image/text input, Gemini model selection, structured field preview, editable schematics, local validation audit and an optional second-pass AI source audit (requires a private Gemini key; the report is not official verification). Its structured suggestions can be retained with an E-Visa draft without applying them to applicant fields until explicit review; raw source files are not saved. A separate **Document OCR** tab retains bundled Sinhala-capable OCR and optional private Surya. The restored **Python Selenium** tab generates candidate-specific, all-section Selenium Python, Playwright Python/Node, a reusable dropdown module, detailed personal-data and stage-by-stage text plans, and downloadable/copyable references. The **DOM / XPath Inspector** retains editable browser-local selectors, shares saved overrides with code generation, and adds a local HTML snapshot XPath tester. The standalone **E-VISA Application Stages** visualizer, **Biometric Photo Preparation** tab/card and **Draft Summary & Manual Review** tab are intentionally removed. The stage-entry selector and form sections remain; draft save and deletion remain available in the header. Python scripts are not executed by this app and never submit automatically. Extractor and OCR suggestions fill only **blank** draft fields after explicit review, preserving registry and manual values; clear a field before deliberately replacing it with a reviewed suggestion.

The original script may discover/upload local documents and optionally attach to an existing Chrome CDP port; it retains legacy selector/default logic. The direct private attached-candidate ZIP is supplied separately and is not in this public source archive. An **alternative conservative local package** retains dry-run, manual stage prompts, opt-in file mapping, and per-click Save/Next confirmations. Neither ZIP bundles actual applicant documents; the web server does not run the browser or read the operator's folder. Source code, public demo data and the eight reference-code tabs contain no attached applicant identity. Links are unpredictable five-minute **same-origin HTTP attachments**. The attached applicant's direct ZIP contains the **byte-identical Python source** renamed from `.txt` to `.py`. For other candidates, only central applicant/folder/URL configuration and person-specific literal values are substituted; the original 96 automation functions are retained. No added preflight, domain guard or Save/Next stop condition changes the original logic. An offline mock confirmed the original Save/Next behavior—including that it may click Next if Save was not found—so inspect the portal before any real run. The full original workflow and Windows launchers have not been live-portal or Windows-tested; inspect values, legacy defaults, dependencies and optional CDP security implications before use.

The registry-backed workspace uses the upstream-style **studio header, stage-entry selector, Master Schematics editor, AI Document Schematics & Extraction Hub, tabbed Python/Playwright code panel, and DOM / XPath Inspector**. The code panel retains the Selenium Python, Playwright Python/Node, personal-data steps, pipeline steps, automation specs, reusable dropdown module, and full-pipeline Playwright tabs. Select a green tab, then click the green **Download** button to save the active `.py`, `.cjs`, or `.txt` file. Download is disabled while generation is pending or failed, rather than silently doing nothing. Each tab produces a candidate-specific reference rather than an upstream sample. The extractor retains categorized source inputs, visual/JSON review, validation audit, editable extracted fields, and optional AI source audit; its document inputs are transient extraction sources, not a supporting-document library. A separate reviewed local OCR tab complements the retained sections; the photo preparation and draft summary views are not mounted. The host app adds registry prefill, persisted E-Visa drafts and explicit review gates.

**Running downloaded scripts:** `python evisa_selenium_reference.py`, `python playwright_visa_workflow.py`, `python evisa_full_playwright_draft.py`, or `node playwright_visa_workflow.cjs` print dry-run plans with no extra browser dependency. To opt in to **local** text-field filling, install `selenium` for Selenium or `playwright` plus Chromium for the Playwright variant, then run the downloaded script with `--fill`. It opens a local browser, asks you to manually log in and navigate to each stage, and attempts only visible text-field entry using unverified selector references. Native dropdowns, navigation, CAPTCHA, saving and submission require manual handling. The `.cjs` Node file works regardless of whether the containing project declares `"type": "module"`. This integration has not been tested against a live portal, so **do not treat the generated script as a verified end-to-end portal automation**.

**Excluded from the web app:** a server-side browser agent, supporting-document management, live CDP console/logs and automatic final submission. The original download includes an **optional local** CDP launcher from the attachment, while the conservative download never uses CDP. No original person-specific sample fields are placed in the integrated source archive. The extractor's example-text button is synthetic and does not create a candidate. The removed photo-preparation UI does not affect the downloaded original automation's separate, unverified photo/face-positioning code. The editor and generated scripts are *not* an official visa-submission integration and have **not been verified against a current live Romanian portal**. Do not run on real records without permission, candidate/URL review and a portal-specific selector test.

## OCR fallback and review

- **Local OCR** is embedded in Application Creation, the E-Visa Document OCR tab, the shared document-upload modal and the Embassy Pending roster uploader. Upload a PNG/JPEG/WEBP or PDF (up to five rendered pages), choose the languages, then click **Extract with local OCR**. When AI extraction fails in these workflows, the same selected document is automatically sent to the local OCR panel; its suggestions still require review before application. Without the optional private neural service, the included [Tesseract.js](https://github.com/naptha/tesseract.js) engine and official `tessdata_best` English (`eng`), Sinhala (`sin`) and Tamil (`tam`) models run on the server, without an AI key or a third-party OCR API. See `ocr-models/LICENSE.txt` and `ocr-models/SOURCE.txt` for licenses and provenance. Recognition compares the original scan with CLAHE contrast-recovered, enlarged/sharpened and (when needed) sparse-text thresholded passes. It ranks passes by recognizable labeled fields and OCR confidence. The operator can inspect alternate passes. These improvements are not a validated handwriting model. Clearly malformed passport suggestions start **unchecked** with a warning. A stronger neural OCR adapter is also available:

  1. On a **separate, sufficiently provisioned private server**, review [Surya's code and model licenses](https://github.com/datalab-to/surya) and install `ocr-service/requirements.txt`. The code is Apache-2.0; **model weights use a modified OpenRAIL-M license with commercial-use conditions**. Do not assume model weights are unrestricted.
  2. From `ocr-service/`, start `uvicorn surya_service:app --host 127.0.0.1 --port 8501 --workers 1` after installing/configuring Surya's own `llama-server` (CPU) or vLLM (GPU) inference backend. Set `SURYA_OCR_URL=http://127.0.0.1:8501/ocr` for the Node app, using a secure private link if on another machine. On first launch the model may download large weights. The same OCR review panel will prefer Surya and fall back to enhanced Tesseract if the sidecar is unavailable.
  3. **Surya model inference could not be run in this ~1 GB demo environment.** The adapter contract was tested with a mock sidecar, *not* with real Surya weights. The public demo uses enhanced Tesseract. Published Sinhala comparisons suggest Surya can outperform Tesseract on specific benchmarks, not that it will read every passport correctly. See the research and deployment notes below.

- **Bilingual CV ingestion:** Section **01 Details** runs AI first; an empty/failed identity extraction opens local OCR *inside the same section* (or use the manual editor), with explicit editable/checkable suggestions. In batch mode each folder follows the same order. A failed AI extraction produces a per-folder **review** state; unreviewed local OCR results are not exported, and an operator must confirm a name/surname or open the full manual editor. Section **02 Signature** tries AI localization/cropping first, then local background removal **only on isolated signature images**; full form/PDF images require an AI bounding box or manual draw/crop to avoid mistaking text for a signature. Always verify the signature preview. No separate “open-source OCR fallback” card remains in Bilingual CV.
- **Model selection on the small demo:** the bundled `tessdata_best` `sin`+`eng` packs and multi-pass image preprocessing run without GPU, extra downloads or external OCR services. [Surya v2](https://github.com/datalab-to/surya) is a better-researched optional neural path on suitable private hardware, but cannot run in this small demo. A [Sinhala TrOCR handwriting checkpoint](https://huggingface.co/eshangj/TrOCR-Sinhala-finetuned) exists, but its card warns about degraded handwriting and mixed-script text; it is **not installed or claimed as validated on old IDs**. A [2026 Sinhala benchmark](https://arxiv.org/html/2606.29378) found a fine-tuned 1B model stronger on printed historical acts, *not* on handwritten identity cards, and it is too heavy for this deployment. No MCP server has been added merely as an OCR label: a protocol by itself cannot increase recognition quality.
- Other three-letter Tesseract packs can be placed in `ocr-models/`; a *private* server can opt into official-model download with `OCR_ALLOW_MODEL_DOWNLOAD=true`. Public demo disables downloads.
- OCR text and label/MRZ-based field **suggestions** are shown to the operator. Check and edit suggested values and select which fields to use; accuracy varies by scan quality, language, layout and document. Sinhala support does **not** mean every Sinhala document or identifier is read correctly. In particular, passport characters can be misrecognized. PDF conversion is capped at five pages and large pages are scaled for processing.
- In Application Creation, selected suggestions populate the editable CV form, **not** the registry. In the shared document-upload modal, choose the **exact existing candidate** and confirm before writing supported reviewed fields to registry, passport, embassy-interview or checklist records. OCR never guesses or creates a candidate. Embassy Pending review rows must have name, passport, SE number, company and applied date before an operator can confirm the batch import; missing fields stay blank instead of being fabricated.
- Gemini-assisted extraction is optional in the upstream e-v extractor and other AI workspaces. Set `GEMINI_API_KEY` in `.env` to enable it. Without a key, `/api/ai/extract-data` returns an honest 503; its explicit-label text-only matcher remains available without a key. It cannot read images; use Document OCR and paste the reviewed text, or provide a private Gemini key. `/api/documents/extract` also returns an honest error rather than inventing identities from filenames. AI suggestions in the shared upload modal also require review and explicit selection of an existing candidate. **Gemini inference has not been tested with a real key here.** Section-specific status changes (such as marking a visa refusal) are **not** automatic just from unreviewed OCR; review and change statuses in the appropriate section.
- The separate Embassy Pending uploader includes a **bundled sample roster** action for demonstrations. It is clearly separate from uploaded-document OCR and must never be mistaken for extracted contents of a new file.

## Run locally

Requires Node.js 20.19+.

```bash
npm install
npm run dev
```

Open `http://localhost:3000`. To try the included **synthetic-only** `ALEX SAMPLE` dataset, run `DATA_DIR="$PWD/demo-data" PUBLIC_DEMO=true npm run dev` instead. For AI extraction set `GEMINI_API_KEY=your_key` in `.env` (see `.env.example`). Manual entry, registry prefill, saved applications, exports and bundled local OCR work without it.

Production-mode local run:

```bash
npm run lint
npm run build
npm run start
```

Set `DATA_DIR=/a/private/data/directory` to relocate the database. For a disposable preview only, `PUBLIC_DEMO=true` shows a public-demo warning and suppresses the base app's automatic candidate seed; **always use an isolated synthetic-data `DATA_DIR` as well**. Do not expose the real registry. This repository has no built-in authentication/authorization; add sign-in, access controls, TLS and secure file storage before using real personal information on the public internet.

## Stable synthetic demo hosting

The distributable ZIP intentionally omits the existing non-synthetic `data/database.json`, test/demo runtime state, and the base project's `scripts/seed-authentic-data.js` (which contains personal records). The bundled `demo-data/database.json` is synthetic. If deploying from the local source checkout instead, remove or protect those personal-data files before publishing a repository.

A `render.yaml` blueprint is included for a Render web service. To deploy it, push this source to a repository you control and create a Render Blueprint from that repository. The blueprint uses only `demo-data/database.json` with `PUBLIC_DEMO=true`; never expose `data/database.json`, `.test-data`, or a real applicant database. Render assigns a persistent HTTPS hostname. Its free plan can sleep when idle, so the first request may take time, and its disk is ephemeral; this blueprint is a disposable demo, not production data storage. Restrict public write access or add authentication before using anything beyond synthetic data. The server binds to `0.0.0.0` and respects the host's `PORT`.

The temporary `trycloudflare.com` quick tunnel is **not reliable hosting**: Cloudflare can disconnect it and return Error 1033 even while the app is running. Do not share a quick-tunnel address as a permanent demo link. Cloudflare's named tunnel also needs an always-on origin and your own Cloudflare account/domain; it is not provisioned by this archive.

## Limits and provenance

The original project's optional Google Apps Script sync remains configured and depends on that external service responding. The integrated app still contains the original system's sample/seed workflows; audit your own dataset before deployment. Local OCR is CPU-intensive and serialized per process with a basic per-IP rate limit; do not treat it as hardened multi-tenant infrastructure. Existing PDF table export uses jsPDF's default fonts, which may not render every non-Latin name; check PDFs when exporting Sinhala/Tamil names. Always secure backups and obtain consent before processing passports or candidate documents.

## OCR research and accuracy caveats

A [2025 Sinhala/Tamil comparison](https://arxiv.org/html/2507.18264v1) reported particularly strong Surya Sinhala results on its evaluated documents, while a [2026 study on degraded real-world Sinhala pages](https://arxiv.org/html/2606.29378) found much higher error rates for generic engines and lower character error with a fine-tuned LightOnOCR model. That study's fine-tuned weights are [private at the time of this integration](https://github.com/avishadilhara/Cross-Temporal-Sinhala-OCR), so they cannot honestly be embedded here. Other OCR toolkits' broad language counts do not by themselves prove Sinhala coverage. **No OCR system can promise correct Sinhala words, names or identifiers on every scan.** Test with your own consented document samples and manually verify every result.
